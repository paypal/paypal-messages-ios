## What this repository is

`PayPalMessages` — the iOS SDK module that renders PayPal pay-later messaging (a banner
offering "Pay in 4", PayPal Credit, and similar). It is the engine behind Braintree's
`BTPayPalMessagingView`: per the README, this module is **intended for use with the
Braintree SDK only**, so a bug reported against `BTPayPalMessagingView` is usually a bug
here.

Swift, UIKit-based, iOS 15+, Xcode 14.3+ / Swift 5.8+. A `Representable` nested type gives
SwiftUI support over the same UIKit view.

## Building and testing — read this first

**`swift build` does not compile this repository.** `Package.swift` declares a
`.binaryTarget` pointing at the released `PayPalMessages.xcframework.zip`, so SPM downloads
a prebuilt binary and never touches `Sources/`. On a non-iOS host it then fails with
`While building for macOS, no library for this platform was found`. That error means "wrong
tool", not "broken code".

The real build is the Xcode project:

```bash
open PayPalMessages.xcworkspace          # Demo app: select the Demo scheme
xcodebuild test -workspace PayPalMessages.xcworkspace \
  -scheme PayPalMessages -destination 'platform=iOS Simulator,name=iPhone 15'
```

This needs **full Xcode** — Command Line Tools alone provide no iOS SDK and no simulator.
If `xcodebuild -version` reports `requires Xcode, but active developer directory is a
command line tools instance`, you cannot build or test this repo at all. Say so plainly
rather than reporting Swift you have never compiled as verified; there is no partial path
here, since even type-checking a single file needs the iOS SDK for `import UIKit`.

`fastlane` drives CI (see `fastlane/` and the `Gemfile`).

Within `Sources/PayPalMessages/`: `PayPalMessageView.swift` (the public `UIControl`),
`PayPalMessageViewModel.swift` (fetch + state, owns the request), `Config/` (the public
config objects), `IO/` (requests, responses, merchant profile), `Delegates/` (the public
state and event protocols), `Utils/` (attributed-string building, parameters, `Proxy`),
`Analytics/`, and `PayPalMessageModal*` for the tap-through modal.

## The view lifecycle, which most questions reduce to

Four behaviours explain nearly every integration problem, and all four are non-obvious:

1. **Constructing the view starts the fetch.** `PayPalMessageView(config:stateDelegate:eventDelegate:)`
   begins loading immediately; there is no separate `start()`. Creating a view early *is*
   prefetching.
2. **A loading view is already ~zero-height.** `intrinsicContentSize` forwards to the internal
   `messageLabel`, which has no text until content arrives. Callers do not need to hide it or
   reserve a placeholder.
3. **`setConfig(_:)` always refetches**, deliberately, even for an equal config. Calling it on
   a reused view discards resolved content and re-issues the request.
4. **Message content is not cached client-side.** `ignoreCache` is a request parameter sent to
   the server, not a local cache switch; only the *merchant profile* is cached, in
   `UserDefaults` via `MerchantProfileProvider`. One view means one network request.

Consequence worth knowing before proposing an API: **content cannot be resolved without a
view.** `MessageRequest` / `MessageRequestable` are internal and the fetch lives in
`PayPalMessageViewModel`, which holds `weak var messageView`. Anything that needs a message's
height or existence *before* a view exists (list row sizing, for example) cannot be done with
today's public API. See `Documentation/ReusableListIntegration.md` and issue #44.

## Conventions

- Public API carries doc comments; the delegate protocols in `Delegates/` are the supported
  extension points (`PayPalMessageViewStateDelegate` for `onLoading`/`onSuccess`/`onError`,
  `PayPalMessageViewEventDelegate` for `onClick`/`onApply`).
- `Proxy`/`AnyProxy` in `Utils/Proxy.swift` forwards the view's stored properties to the view
  model — add a new configurable property in both places, not just the view.
- Tests use hand-written mocks (`PayPalMessageRequestMock`, `MerchantProfileRequestMock`, …)
  rather than a mocking framework; follow that when adding one.
- Commits follow Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`) — releases are cut
  from them by semantic-release, so the prefix decides the version bump.
- `CHANGELOG.md` is generated by the release job. Do not hand-edit it.

## Scope

This is a published payments SDK: its public API is a compatibility contract, and changes to
it are the maintainers' call. Prefer answering an integration question with documentation or
a demo over adding API surface. If a genuine gap needs new API, describe the gap and propose
the shape in an issue first rather than opening a PR that presumes the design.
